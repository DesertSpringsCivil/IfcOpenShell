# Documentation and Community Critique: Saikei Grading & Earthwork Spec

**Reviewer:** saikei-docs agent
**Date:** 2026-04-24
**Subject:** [Saikei_Grading_Earthwork_Spec.md](Saikei_Grading_Earthwork_Spec.md) (updated draft, April 24 2026)
**Companion context:** [Saikei_Grading_Earthwork_Research.md](Saikei_Grading_Earthwork_Research.md), [Saikei_Grading_Earthwork_Spec_IFC_Critique.md](Saikei_Grading_Earthwork_Spec_IFC_Critique.md)

The spec is excellent as an implementation brief for agents. As a foundation for documentation and community positioning, it has notable strengths but leaves several concrete gaps that need explicit commitment before Sprint 1 documentation is authored. What follows is organized by the ten axes, with a concrete doc plan at the end.

---

## 1. Two-Persona Doc Coverage

**Assessment: single-persona — the spec is written entirely for agents and developers, with no commitment to an interactive-user path.**

The spec's header reads "Agent implementation guide." Section 11 (Work Breakdown) assigns documentation tasks: "Surface module README, CLAUDE.md update" (Sprint 1, 100 LoC), "Grading module README + tutorial (flat pad to existing ground)" (Sprint 2, 100 LoC), "Earthwork README + workflow example" (Sprint 3, 50 LoC). These are all internal agent-facing documents.

There is zero mention of a panel walkthrough, a UI screenshot sequence, a "how to grade a pad" step-by-step for an engineer clicking through Bonsai's T-panel, or any Blender-centric workflow narrative. The interactive-engineer persona is completely absent from the documentation plan.

For the agent/developer persona, the spec provides dense Python API signatures across sections 5, 7.1, and 7.2. Those signatures are usable by a developer reading code, but they are not structured for programmatic consumption by an LLM agent at runtime (no docstrings, no parameter annotations in the spec, no tool-call schema). The spec commits to operator names (`CIVIL_OT_surface_create_from_points`, etc.) but does not commit to what Python callable they expose for headless invocation.

**Gap:** The spec must explicitly bifurcate documentation requirements: for every major workflow, name both a UI walkthrough target and a Python API reference target. Currently neither is fully specified.

## 2. API Reference Format

**Assessment: implicit in docstrings, but no format commitment.**

The spec's tool-method stubs in sections 7.1 and 7.2 have inline docstrings that describe behavior adequately for implementation. However:

- No parameter types are annotated in the signatures in the spec (the actual Python code does have type hints per the dataclasses, but the spec's method stubs strip them).
- No return types are shown for most tool methods (the `static def z_at` and `static def build_tin_from_points` are exceptions).
- No Sphinx-style docstring format (`Args:`, `Returns:`, `Raises:`) is prescribed.
- No decision on whether autogenerated docs (Sphinx/autodoc) or hand-written reference is the target.

Bonsai does not currently use Sphinx. Writing API reference as hand-maintained Markdown in each module's `README.md` is the de facto Saikei pattern so far. That approach degrades quickly once tool.py files reach ~1,000 lines.

**Recommendation.** Adopt Google-style docstrings throughout `tool/surface.py`, `tool/grading.py`, `tool/earthwork.py`, and `core/surface.py` etc. from the first commit. This serves three audiences simultaneously: (a) IDE hover-help for human developers, (b) LLM context injection when agents are given a file to read, and (c) future Sphinx autodoc if the project grows to warrant it. The docstring format is machine-readable enough for an LLM to act on without a separate manifest. No new tooling is needed for Sprint 1.

For agent-facing consumption specifically, a single `docs/grading/api_reference.md` file that lists every public tool method with its signature, parameter semantics, and return type would serve better than scattered file-level READMEs. This file can be machine-generated from docstrings using `pydoc` or a 20-line script — no Sphinx dependency required.

## 3. Example-Driven Documentation

**Assessment: one example mentioned (flat pad), no canonical set defined.**

The spec references "flat pad to existing ground" as the Sprint 2 tutorial target. Sprint 3 offers "full pad → cut/fill report → IFC export." That is the extent of worked-example commitment.

Civil engineers learn by recognizing their problem in an example. The research doc explicitly covers parking lots, ponds, and building pads as the primary use cases. The spec's own dataclass comments reference "pond-like grading" as a test case. Yet the documentation plan does not commit to a canonical example set.

**Recommended canonical set for the documentation suite (in order of complexity):**

1. **Flat building pad** — single feature line (closed rectangle), flat interior fill, slope ties to existing ground at 3:1 fill. The simplest possible grading problem. Every civil engineer who has used Civil 3D knows this as the first exercise. Tests: `interior_fill="flat"`, cut/fill both present, single grading group.

2. **Sloped parking lot** — closed polygon feature line with varying vertex elevations (2% cross-slope), no interior fill override, ties to existing ground. Tests: `interior_fill="interpolate_from_boundary"`, no cut (all fill scenario), multiple criteria on one feature line.

3. **Retention pond** — closed polygon feature line at low elevation, surrounding the pond footprint, fills to existing ground on the outside, pond floor below existing ground. Tests: cut-dominant scenario, `interior_fill="flat"` at pond bottom elevation, `IfcEarthworksCut` authoring.

4. **Road embankment segment** — open feature line (road shoulder edge), ties to existing ground, one side only, adjacent to a named `IfcAlignment`. Tests: `Pset_SaikeiGradingAlignment` with station range, open feature line with "apply to side" direction, alignment cross-reference.

Examples 1-3 can be completed in Sprints 1-3 respectively and should ship with the sprint. Example 4 bridges into the vertical alignment and corridor work and can be a Sprint 3 stretch target.

Each example should exist as a checked-in IFC file in `docs/examples/` and a companion Python script that reproduces it from scratch using only the public core API — no Blender, no operators. That script is simultaneously the integration test and the agent-facing API documentation.

## 4. IFC Round-Trip Demo

**Assessment: not in the spec as a public artifact commitment.**

The spec mentions validation at several points: "round-trip tests (write → read → compare) through `ifcopenshell`" (Sprint 1), "IFC round-trip through DESITE or bSI reference validator" (Sprint 3), and section 10 acknowledges that viewer support is limited to IFC 4.3 civil tools.

What is missing is a commitment to a **public, shareable IFC artifact** — a file that a buildingSMART member, a reviewer, or a potential user can download, open in the bSI reference validator or DESITE, and confirm it is valid IFC 4.3. Currently the test suite validates the file through ifcopenshell's own reader, which is not the same as a third-party validation.

For buildingSMART credibility specifically, the round-trip story needs to be: Saikei authors the file → file passes bSI reference validator → file opens in at least one non-Saikei viewer (DESITE is the most accessible; FZK Viewer also supports geotechnical entities) with surfaces rendering correctly → file re-opens in Saikei and is editable.

This demo does not need to be fully polished before Sprint 1. It should be committed to as a Sprint 3 deliverable and treated as a documentation artifact, not just a test. The file belongs in `docs/examples/round_trip_demo.ifc` with accompanying `docs/examples/round_trip_demo_notes.md` describing what was validated.

**For grant alignment:** this is the artifact that converts the NLnet application from "we plan to implement IFC 4.3 civil" to "here is a valid IFC 4.3 file produced by our open-source tool." That difference is material to NLnet reviewers.

## 5. Grant and Stakeholder Vocabulary

**Assessment: partially present in the spec, absent from the documentation plan.**

The spec uses correct IFC 4.3 entity names throughout. It references IRROADWP3 Annex I (the buildingSMART infrastructure working paper), OmniClass Table 22, CSI MasterFormat Division 31, and `IfcTriangulatedIrregularNetwork`. These are the right terms.

However, the spec never uses the phrase "IFC 4.3 infrastructure domain," never mentions "buildingSMART International (bSI)," never mentions AASHTO BIM requirements for State DOTs, and never frames the feature in terms of a gap it fills in the existing ecosystem.

For grant narratives and stakeholder pitches, the vocabulary that lands is:

- **"First open-source implementation of `IfcTriangulatedIrregularNetwork` + `IfcEarthworksCut`/`IfcEarthworksFill` authoring"** — this is a factual and auditable claim if it holds up.
- **"IFC 4.3 infrastructure domain compliance"** — the bSI classification that differentiates civil IFC from building IFC.
- **"IRROADWP3-aligned earthworks model"** — the spec references this document, which is the buildingSMART infrastructure working paper that defines the conceptual model Saikei implements.
- **"Enables State DOT IFC 4.3 compliance workflows"** — the AASHTO BIM guide and several State DOT BIM requirements (WSDOT, CDOT) specify IFC 4.3 for infrastructure deliverables, including earthwork quantities.

None of this vocabulary is in the spec's documentation tasks. A brief "Grant and outreach vocabulary" section in the sprint 3 doc plan, listing the auditable claims this feature enables, would allow grant narrative writers to work from the spec rather than from memory.

## 6. Changelog and Incremental Release Structure

**Assessment: not addressed anywhere in the spec.**

The spec uses a three-sprint model (Sprint 1: surfaces, Sprint 2: grading, Sprint 3: earthwork volumes). These are plausibly three separate user-facing releases. But the spec does not address:

- What a user gets after Sprint 1 that is useful in isolation (answer: a TIN surface viewer and IFC terrain import/export — that is useful).
- Whether Sprint 2's grading capability is useful without Sprint 3's volume calculation (answer: probably yes — you can design the grade before computing volumes).
- How the changelog should communicate this to engineers who may adopt the tool between sprints.

The Keep a Changelog format used in the rest of Saikei is sufficient. The concern is specificity: the sprint doc tasks ("Surface module README") do not specify whether a changelog entry is required or what user-facing language to use.

**Recommendation.** Each sprint should produce exactly one changelog block following this pattern:

```
## [0.8.x] — Sprint 1 (Terrain Surfaces)
### Added
- Create existing-ground surface from XYZ/CSV point cloud (IfcGeotechnicalStratum)
- Constrained Delaunay triangulation with breakline support
- Export terrain surface as IFC 4.3 IfcTriangulatedIrregularNetwork
- Vertical datum support (NAVD88/NGVD29) via IfcProjectedCRS
```

The key is user-facing language ("create existing-ground surface from XYZ/CSV") alongside the IFC entity name. Civil engineers who use the tool need the first; buildingSMART reviewers and grant officers need the second. Both audiences read the same changelog entry.

Adoptability concern specific to the multi-sprint rollout: engineers who start with Sprint 1 surfaces need to know that their IFC files authored with Sprint 1 will be forward-compatible with Sprint 2 grading. The spec commits to this implicitly (same `IfcGeomodel` / `IfcGeotechnicalStratum` hierarchy throughout), but it should be stated explicitly in Sprint 1 release notes: "surfaces authored in this sprint will be compatible with the Sprint 2 grading module."

## 7. Terminology Consistency

**Assessment: mostly consistent, with two specific gaps.**

The spec does well overall. It uses "cut" and "fill" consistently (not "excavation" and "embankment" interchangeably), it uses "daylight line" (not "tie-in line" or "slope intercept"), it uses "feature line" (matching Civil 3D's term exactly). The slope ratio notation `3.0` meaning "3:1 (H:V)" is named explicitly in the `GradingCriteria` docstring. This is good.

Two gaps:

**"Interior fill" vs. "pad subgrade."** The spec uses "interior fill" as the term for the flat or interpolated surface inside a closed feature line. Civil engineers more commonly call this the "pad subgrade" or simply "the pad." The four strategy options (`none`, `flat`, `interpolate_from_boundary`, `from_surface`) use developer vocabulary, not civil engineering vocabulary. In UI and documentation, these should have civil-facing labels: `none` → "open (no interior)", `flat` → "flat at average elevation", `interpolate_from_boundary` → "interpolated from edge elevations", `from_surface` → "from reference surface." The Python enum values can stay as-is; the displayed names in docs should not.

**"Proposed_group" vs. "proposed_site" surface kinds.** These are Saikei-internal classification terms that do not correspond to any civil engineering concept engineers know. Documentation must map these to user language: "proposed_group" = "grading group surface (one feature's proposed grade)" and "proposed_site" = "composite site surface (all features merged)." If documentation uses the Python literal strings without explanation, engineers will be confused.

## 8. Agent-Facing Documentation

**Assessment: the spec provides API structure but no agent-consumable surface is defined.**

The spec's core and tool method signatures in sections 7.1 and 7.2 are well-formed and could be consumed by an LLM agent that is given the spec to read. However, that is ad-hoc — it relies on the agent reading a multi-thousand-word document and extracting function signatures.

**For robust agent-driven usage, three surfaces should exist:**

**a. Core function signatures as a machine-readable manifest.** A file `docs/grading/api_manifest.json` listing every public core function with its name, parameters (name, type, description), return type, and a one-line description. This is trivially generated from docstrings using `inspect` + a 30-line script. An LLM agent given this file can plan a grading workflow without reading source code. The manifest format should match the existing MCP tool-call schema pattern (name, description, inputSchema as JSON Schema) so it is directly usable as an MCP tool definition if a Saikei MCP server is ever built.

**b. Headless usage example.** A file `docs/grading/headless_example.py` showing the complete flat-pad workflow using only `import ifcopenshell`, `from bonsai.core import surface, grading, earthwork`, and `from bonsai.tool import Surface, Grading, Earthwork` — no `bpy`, no Blender context. This is the example agents run. It requires that the core and tool layers are actually importable without Blender, which the 3-layer architecture mandates. If this example cannot be written, it reveals that the architecture has leaked Blender dependencies into the core or tool layer.

**c. MCP server stub.** Not for Sprint 1, but the doc plan should name it as a Sprint 3 or post-MVP deliverable: a `tools/saikei_mcp_server.py` that wraps the core grading functions as MCP tool calls. The server would expose `create_surface`, `add_breakline`, `create_grading_group`, `add_grading_object`, `compute_earthwork_volumes` as tools. This is low implementation cost if the core API is clean (each function maps to one tool). The manifest described in (a) would serve as the schema source. Placing this in the doc plan now means architecture decisions in Sprint 1-3 keep agent invocability in mind rather than retrofitting it later.

**Where these live:** `docs/grading/` alongside the module READMEs. Not in the source tree, not in test fixtures — in a user/agent-facing documentation directory that is findable without reading source code.

## 9. Community Outreach Moments

**Assessment: no outreach milestones named in the spec.**

The spec is an implementation document; community outreach is not its job. But the doc plan should name the moments, because some require lead time (coordinating with Dion for an OSArch post, preparing a buildingSMART data drop).

**Milestone 1 — Sprint 1 merge: "Saikei can now model and export terrain surfaces in IFC 4.3."**
Target: OSArch community forum post. Narrative: "We've added the first open-source tool for authoring `IfcTriangulatedIrregularNetwork` with constrained Delaunay triangulation and breakline support. You can import an XYZ point cloud, add breaklines, set holes and voids, and export a valid IFC 4.3 terrain file. Here's a demo." Attach the Sprint 1 round-trip IFC file and the bSI validator screenshot. This is a factual milestone that the OSArch audience can evaluate immediately.

**Milestone 2 — Sprint 2 merge: "Saikei can design a graded pad with slope ties and daylight lines."**
Target: LinkedIn post + OSArch. Narrative: "Civil engineers can now draw a feature line in Bonsai, apply a grading criteria (e.g., 3:1 fill, 2:1 cut), and compute the slope projection to existing ground. The result writes to IFC 4.3 as `IfcEarthworksFill[SLOPEFILL]`. Free, no subscription." Include a short screen recording of the pad grading workflow. This is the milestone that converts skeptical engineers — it demonstrates the core Civil 3D workflow.

**Milestone 3 — Sprint 3 merge: "Saikei computes cut and fill volumes, writes standard IFC Qtos."**
Target: buildingSMART forum, LinkedIn, OSArch, and a direct email to Will Sharp at bSI. Narrative: "Saikei now computes earthwork volumes via TIN-to-TIN prismoidal method and writes `Qto_EarthworksCutBaseQuantities` and `Qto_EarthworksFillBaseQuantities` to standard IFC 4.3. Quantities are discoverable by Solibri, CostX, and any IFC 4.3-compliant QTO tool. The IFC file passes the bSI reference validator. Open source, GPL v3, runs in Blender 5.0." Attach the round-trip demo IFC file.

The buildingSMART outreach at Sprint 3 is the highest-value community moment and should be treated as a project milestone with the same priority as code delivery. Will Sharp's positive earlier response makes this a warm contact.

## 10. Licensing and Attribution

**Assessment: partially addressed, with one specific gap.**

The spec's references section (section 13) cites the IFC 4.3 buildingSMART docs, the IRROADWP3 report, OmniClass, the Shapely and SciPy docs, and the Autodesk Civil 3D help. This is adequate attribution for the conceptual model sources.

The specific gap: **the slope projection algorithm in section 6.2 is not attributed.** The "march outward at chosen slope until intersection" algorithm is a standard numerical technique, but it is described in detail in specific Civil 3D references and in published civil engineering textbooks (notably Uren & Price "Surveying for Engineers," and the ASCE Surveying Engineering guides). The spec's algorithm description is original but is clearly derived from Civil 3D's behavior. That is fine — Civil 3D's behavior follows industry-standard practice. But a brief note in the algorithm section ("This approach follows the standard grade-point projection method described in [Civil 3D help reference] and common to all feature-line-based grading tools") would preempt any attribution questions from OSArch or buildingSMART reviewers who might wonder whether proprietary algorithms were reverse-engineered.

The SciPy Delaunay and Shapely CDT citations are appropriate and sufficient for the triangulation backend. No additional attribution is needed there.

## Concrete Documentation Plan

**Directory structure (additions to existing repo layout):**

```
docs/
├── grading/
│   ├── overview.md                    # two-paragraph feature description, persona overview
│   ├── api_reference.md               # all public core + tool methods, Google docstring format
│   ├── api_manifest.json              # machine-readable function manifest (MCP-compatible schema)
│   ├── headless_example.py            # complete flat-pad workflow, no bpy, agent-runnable
│   ├── ui_walkthrough_surface.md      # Sprint 1: interactive engineer path, step-by-step
│   ├── ui_walkthrough_grading.md      # Sprint 2: feature line → grading group → daylight line
│   ├── ui_walkthrough_earthwork.md    # Sprint 3: compute volumes → cut/fill map → export
│   └── terminology.md                 # term glossary (cut/fill, daylight, interior fill, etc.)
├── examples/
│   ├── flat_pad/
│   │   ├── flat_pad.py                # Python script (agent-runnable, no bpy)
│   │   └── flat_pad.ifc               # generated IFC file (checked in)
│   ├── sloped_parking_lot/
│   │   ├── sloped_parking_lot.py
│   │   └── sloped_parking_lot.ifc
│   ├── retention_pond/
│   │   ├── retention_pond.py
│   │   └── retention_pond.ifc
│   ├── road_embankment/
│   │   ├── road_embankment.py         # Sprint 3 stretch
│   │   └── road_embankment.ifc
│   └── round_trip_demo/
│       ├── round_trip_demo.ifc        # Sprint 3 deliverable — passes bSI validator
│       └── round_trip_demo_notes.md   # what was validated, which viewers opened it
└── outreach/
    ├── sprint1_osarch_post.md         # draft post text, links, validator screenshot
    ├── sprint3_bsi_email.md           # draft outreach to Will Sharp
    └── grant_vocabulary.md            # auditable claims for NLnet/bSI grant narratives
```

**Tooling decisions:**
- Docstrings: Google style in all new `core/` and `tool/` files from first Sprint 1 commit.
- API manifest: 30-line Python script `tools/generate_api_manifest.py` run as part of CI when tool files change.
- No Sphinx — not worth the setup cost for the current project size.
- UI walkthroughs: hand-written Markdown with annotated screenshots. One per sprint, merged with the sprint code.
- Example IFC files: generated by the companion `.py` scripts, regenerated in CI to prevent drift.

**Sprint-by-sprint doc deliverables (replacing the current "100 LoC README" placeholders):**

Sprint 1: `docs/grading/overview.md`, `docs/grading/terminology.md`, `docs/grading/ui_walkthrough_surface.md`, `docs/examples/flat_pad/`, `CHANGELOG.md` Sprint 1 entry, `docs/grading/api_manifest.json` skeleton.

Sprint 2: `docs/grading/api_reference.md` (surface + grading sections), `docs/grading/ui_walkthrough_grading.md`, `docs/examples/sloped_parking_lot/`, `docs/examples/retention_pond/`, `CHANGELOG.md` Sprint 2 entry, `docs/grading/headless_example.py`.

Sprint 3: `docs/grading/ui_walkthrough_earthwork.md`, `docs/examples/road_embankment/`, `docs/examples/round_trip_demo/`, `docs/outreach/` directory, `CHANGELOG.md` Sprint 3 entry, `api_manifest.json` finalized.

**Agent-facing API surface (summary):** Google-style docstrings in source files + `api_manifest.json` in MCP tool-call schema format + `headless_example.py` per workflow. The manifest is the lightweight alternative to a full MCP server and requires no new infrastructure. A Saikei MCP server wrapping these functions is named as a post-Sprint 3 deliverable, not a Sprint 1 requirement.
