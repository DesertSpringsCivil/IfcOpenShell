# Spec v3.2.5 amendments — queued

Items the Phase 4 surface module and Phase 5 grading module surface that the
spec (currently v3.2.4) should eventually catch up to. **No rush.** Bundle
all of these into a single v3.2.5 patch at the next natural break point —
target is **right after Phase 5 ships and before Phase 6 starts**.

The Phase 4 + Phase 5 implementations are accurate today; the spec is
running one version behind on a handful of decisions that future
implementers (or sub-agents reading the spec cold) would otherwise
misread.

## Queue

1. **§8.3 / §9 — elevation banding via `SurfaceDecorator` (not mesh
   `color_attributes`).** Spec wording says "mesh with vertex colors";
   Phase 4 ships a one-class `SurfaceDecorator` with the
   `SMOOTH_COLOR` GPU shader and per-vertex Z-derived colors drawn at
   `POST_VIEW`. Already flagged in the Phase 4 handoff doc, never
   actually written into the spec. Worth a short paragraph clarifying
   that vertex-color-attributes is not the Bonsai pattern; the
   decorator approach matches the 14 other Bonsai visualization
   modules.

2. **G-key conflict resolution policy.** Both `tool.Surface`
   (breakline picker, when its modal version ships in 4.1+) and
   `tool.Grading` (feature-line elevation edit) want G-key. Phase 5
   commit 12 introduces an `is_feature_line_edit_active` helper
   convention — only the modal whose edit-mode bool is set responds
   to G-key. Spec §8.4 already partitions G-key by mode but doesn't
   spell out the helper-function convention or how new modes should
   register.

3. **Slope projection tunables and their committed defaults.** Phase 5
   commit 3 lands concrete values for the three tunables that affect
   slope projection accuracy:
   - **Sample step size** along feature-line segments (committed
     default: TBD — likely 0.5 m or 1.0 m; document the trade-off).
   - **Daylight ε** — distance threshold for declaring "the projection
     hit the surface" (committed default: TBD — likely 1e-3 m).
   - **Max-iter cap** for the marching loop — guards against infinite
     loops on degenerate inputs (committed default: TBD — likely
     10⁴ iterations per sample point).

   Spec §6.2 names the algorithm but doesn't pin these. Pin them in
   v3.2.5 so future tunable adjustments are reviewable changes, not
   silent constant edits.

4. **Modal vs draft state for cascade rebuilds — "rebuild on commit,
   not per-modal-frame."** When the user is dragging a feature-line
   vertex with G-key, the grading group's composite proposed surface
   should NOT recompute on every mouse-move event (would crater
   interactivity). Rebuild fires once on modal confirm (Enter/LMB);
   modal cancel discards the draft. Spec §6.3 describes the rebuild
   but is silent on when it fires. Add a "Cascade rebuild policy"
   sub-section.

5. **§7.1 tool-method names diverge from the implementation.** The
   spec lists fictional finer-grained methods (``author_ifc_group``,
   ``author_ifc_composite_fill``, ``apply_source_pset``,
   ``author_ifc_criteria_template``, ``author_ifc_slope_fill``,
   ``add_to_group``, ``create_group``, ``build_criteria``,
   ``get_criteria``, ``apply_elevation_edits``,
   ``update_ifc_alignment_representation``,
   ``find_groups_using_feature_line``, ``update_blender``) that
   correspond to a different decomposition than the shipped
   implementation. Phase 5 collapses several of these into the Phase 2
   API wrappers (``author_group`` does group + composite + source pset
   in one call; ``assign_criteria`` replaces ``add_to_group`` +
   ``apply_source_pset``). The implementation matches the Phase 2 API
   boundary; the spec needs to follow. Update §7.1 to list the actual
   tool surface.

6. **Composite proposed-surface flag computation (Hole=-1).** Spec §6.3
   last paragraph requires Flag=-1 (Hole) for fall-through to existing
   ground in regions of the composite proposed surface that don't
   modify the existing ground. Phase 5 commit 6/7 currently writes
   ``triangle_flags = np.zeros(...)`` for the composite — all-visible,
   no fall-through. Acceptable Phase 5 MVP; required before Phase 6
   cross-surface volume composition. Document the gap explicitly so
   Phase 6 implementers know the composite needs flag computation
   before TIN-to-TIN prismoidal volumes are correct.
