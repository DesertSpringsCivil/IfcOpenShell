# Cross-Section Profiles — Feature Spec

## Overview

Add cross-section profile (assembly/template) support to Saikei. This is the IFC equivalent of Civil 3D assemblies or OpenRoads templates — a parametric definition of a roadway's typical cross-section that can be swept along an alignment to create corridor geometry.

**Critical design choice:** We use **open profiles** (`IfcOpenCrossProfileDef`) swept via **`IfcSectionedSurface`**, NOT closed profiles with `IfcSectionedSolidHorizontal`. Open profiles represent the road surface as lines with widths and slopes. This is the IFC 4.3 preferred approach for roadway design and matches how engineers actually think — in terms of lane widths, cross-slopes, and break points, not closed polygons.

**Point controls via Tags:** Every break point in a cross-section gets a tag (e.g., "CL", "ETW_L", "EPS_R"). When the corridor sweeps profiles along the alignment, points with matching tags in consecutive sections are connected by longitudinal breaklines. Changing a tagged point's position at one station propagates smoothly — this IS the point control system.

---

## The Two IFC Approaches (and Why We Choose Open)

### Approach 1: Open Profiles + Surface (OUR APPROACH)

```
IfcOpenCrossProfileDef → IfcSectionedSurface
```

- Profile defined by widths and slopes (how engineers think)
- ProfileType = CURVE (open line, not closed area)
- Tags on every break point for interpolation control
- Creates a surface, not a solid
- Native support for varying cross-sections (different number of points at different stations via tag branching)
- The buildingSMART-recommended approach for roadway top surfaces

### Approach 2: Closed Profiles + Solid (NOT our primary approach)

```
IfcArbitraryClosedProfileDef → IfcSectionedSolidHorizontal
```

- Profile defined as a closed polygon (points forming a loop)
- ProfileType = AREA
- Creates a solid volume
- Useful for pavement layer volumes, earthwork quantities
- All sections must have identical structure (same number of points, same subtypes)
- May be used later for individual material courses (IfcCourse, IfcPavement)

**We may create closed solids later** for quantity takeoffs, but the primary design workflow uses open profiles.

## IFC Entity Structure

### IfcOpenCrossProfileDef (The Profile)

```
ENTITY IfcOpenCrossProfileDef
  SUBTYPE OF (IfcProfileDef);
  HorizontalWidths : IfcBoolean;
  Widths : LIST [1:?] OF IfcNonNegativeLengthMeasure;
  Slopes : LIST [1:?] OF IfcPlaneAngleMeasure;
  Tags : OPTIONAL LIST [2:?] OF IfcLabel;
  OffsetPoint : OPTIONAL IfcCartesianPoint;
WHERE
  CorrectProfileType : SELF\IfcProfileDef.ProfileType = CURVE;
  CorrespondingSlopeWidths : SIZEOF(Slopes) = SIZEOF(Widths);
  CorrespondingTags : (NOT EXISTS(Tags)) OR (SIZEOF(Tags) = SIZEOF(Slopes) + 1);
END_ENTITY;
```

**Key attributes:**

| Attribute | Type | Description |
|-----------|------|-------------|
| HorizontalWidths | Boolean | `True` = widths measured horizontally (typical). `False` = widths measured along slope |
| Widths | List of float | Width of each segment (lane, shoulder, etc.) |
| Slopes | List of float | Cross-slope of each segment (radians). Positive = upward left-to-right |
| Tags | List of string | One tag per break point. Count = Widths count + 1 (includes start point) |
| OffsetPoint | Optional point | Offset from alignment origin. Usually (0,0) for centerline-based profiles |

**Example — simple two-lane road (half-section, right side):**

```
IfcOpenCrossProfileDef(
    ProfileType = .CURVE.,
    HorizontalWidths = .T.,
    Widths = [3.6, 2.4],           # 3.6m lane + 2.4m shoulder
    Slopes = [-0.02, -0.04],       # -2% lane slope, -4% shoulder slope
    Tags = ["CL", "ETW_R", "EPS_R"]  # 3 points = 2 segments + 1
)
```

This defines 3 break points:
```
CL (0,0)  ──[-2%]──  ETW_R (3.6, -0.072)  ──[-4%]──  EPS_R (6.0, -0.168)
```

### IfcSectionedSurface (The Sweep)

```
ENTITY IfcSectionedSurface
  SUBTYPE OF (IfcSurface);
  Directrix : IfcCurve;
  CrossSectionPositions : LIST [2:?] OF IfcAxis2PlacementLinear;
  CrossSections : LIST [2:?] OF IfcProfileDef;
WHERE
  AreaProfileTypes : profiles must be CURVE type;
  CorrespondingSectionPositions : section count = position count;
  DirectrixIs3D : Directrix.Dim = 3;
  NoOffsets : no lateral/vertical/longitudinal offsets in positions;
  SectionsSameType : all sections must be same subtype;
END_ENTITY;
```

The surface is generated by:
1. Placing each `IfcOpenCrossProfileDef` at its station along the directrix
2. Connecting points with matching tags between consecutive sections
3. Linear interpolation between matched points creates longitudinal breaklines
4. The resulting surface is a triangulated mesh between breaklines

### Cross-Section Positioning

```
IfcAxis2PlacementLinear
└── Location: IfcPointByDistanceExpression
    ├── DistanceAlong: float (station value)
    ├── OffsetLateral: NOT ALLOWED for IfcSectionedSurface
    ├── OffsetVertical: NOT ALLOWED for IfcSectionedSurface
    └── OffsetLongitudinal: NOT ALLOWED for IfcSectionedSurface
```

Note: `IfcSectionedSurface` is stricter than `IfcSectionedSolidHorizontal` — NO offsets allowed in positions.

## The Tag System — Point Controls

Tags are how engineers control the corridor. Each tag represents a named break point that can be independently manipulated at any station.

### Standard Tag Set

```python
class StandardTags:
    """Standard point tags for IFC interoperability."""
    # Centerline
    CL = "CL"          # Centerline / crown point

    # Traveled way
    ETW_L = "ETW_L"    # Edge of traveled way, left
    ETW_R = "ETW_R"    # Edge of traveled way, right

    # Pavement edge
    EPS_L = "EPS_L"    # Edge of pavement/shoulder, left
    EPS_R = "EPS_R"    # Edge of pavement/shoulder, right

    # Curb points
    BC_L = "BC_L"      # Back of curb, left
    BC_R = "BC_R"      # Back of curb, right
    FL_L = "FL_L"      # Flowline/gutter, left
    FL_R = "FL_R"      # Flowline/gutter, right

    # Beyond pavement
    HG_L = "HG_L"      # Hinge point (shoulder break), left
    HG_R = "HG_R"      # Hinge point (shoulder break), right
    DL_L = "DL_L"      # Daylight point, left
    DL_R = "DL_R"      # Daylight point, right

    # Sidewalk
    SW_L = "SW_L"      # Sidewalk edge, left
    SW_R = "SW_R"      # Sidewalk edge, right
```

### How Tags Enable Point Controls

**Scenario: Lane widening on a curve**

At station 100+00 (tangent):
```
Tags:   ["CL", "ETW_R", "EPS_R"]
Widths: [3.6, 2.4]     # Standard 3.6m lane
```

At station 105+00 (curve — widen for trucks):
```
Tags:   ["CL", "ETW_R", "EPS_R"]
Widths: [4.2, 2.4]     # Widened to 4.2m lane
```

Because both sections have the same tags, the IFC viewer interpolates smoothly between them. The lane width transitions from 3.6m to 4.2m over 500m. The engineer controlled this by changing ONE number at ONE station — that's a point control.

**Scenario: Adding a turn lane (tag branching)**

At station 100+00 (no turn lane):
```
Tags:   ["CL", "ETW_R", "EPS_R"]
Widths: [3.6, 2.4]
```

At station 102+00 (turn lane starts):
```
Tags:   ["CL", "ETW_R", "TL_R", "EPS_R"]
Widths: [3.6, 3.6, 2.4]
```

The `IfcSectionedSurface` handles this via tag branching — the "TL_R" tag appears at station 102+00, creating a new breakline that branches off from "ETW_R". This is a powerful IFC 4.3 capability that maps directly to Civil 3D's widening functionality.

## Component-Based Assembly Architecture

Saikei should model cross-sections as collections of **components** (matching Civil 3D subassemblies / OpenRoads components). Each component contributes widths, slopes, and tags to the final profile.

### Component Types

| Component | Typical Widths | Typical Slopes | Tags Generated |
|-----------|---------------|----------------|---------------|
| Lane | 3.0-4.2m | -1.5% to -2.5% | ETW |
| Shoulder | 1.2-3.0m | -2% to -6% | EPS, HG |
| Curb | 0.15-0.6m | vertical or sloped | BC, FL |
| Gutter | 0.3-0.6m | -5% to -8% | FL |
| Sidewalk | 1.2-2.4m | -1% to -2% | SW |
| Ditch | 0.6-3.0m | variable | DL |
| Median | 0.6-18.0m | variable | MED |

### Assembly Construction (Left-to-Right from Centerline)

An assembly is built outward from the centerline. Each side (left/right) has its own chain of components:

```
         Left Side                    CL                    Right Side
    ←──────────────────               │               ──────────────────→
    DL_L  HG_L  EPS_L  ETW_L         │         ETW_R  EPS_R  HG_R  DL_R
     │      │      │      │           │           │      │      │      │
     ├──────┤──────┤──────┤───────────┤───────────┤──────┤──────┤──────┤
     Ditch  Shldr  Lane   Lane       Crown       Lane   Lane   Shldr  Ditch
```

Each component connects to the previous component's endpoint. The assembly's `to_ifc_open_profile()` method concatenates all widths, slopes, and tags into a single `IfcOpenCrossProfileDef`.

### Half-Section vs Full-Section

For IFC, we can either:
- **Full section:** One `IfcOpenCrossProfileDef` spanning left ditch to right ditch (simpler, one entity)
- **Half sections:** Separate left and right profiles (allows independent superelevation per side)

Recommendation: Start with **full section** for simplicity. A full section with `OffsetPoint` at the centerline covers most use cases.

## Visualization Strategy — Geometry Engine Limitation

**Important:** As of March 2026, IfcOpenShell's geometry engine (IfcConvert / `create_generic_shape()`) does NOT support `IfcOpenCrossProfileDef`. Rick Brice filed [IfcOpenShell #7338](https://github.com/IfcOpenShell/IfcOpenShell/issues/7338) about this — when he tried to use `IfcOpenCrossProfileDef` with `IfcSectionedSurface`, the geometry engine returned "Unexpected topology" because there's no C++ implementation for this entity type yet.

**What this means for Saikei:**

- We CAN create valid `IfcOpenCrossProfileDef` and `IfcSectionedSurface` IFC entities ✅
- The IFC files will be schema-compliant and readable by future software ✅
- But `tool.Loader.create_generic_shape()` CANNOT generate Blender meshes from them ❌

**Our approach — dual path:**

1. **IFC layer:** Create correct `IfcOpenCrossProfileDef` + `IfcSectionedSurface` entities for standards compliance and file interoperability.

2. **Blender preview layer:** Compute cross-section geometry ourselves from the widths/slopes/tags data and create Blender meshes directly (polylines for 2D preview, surface mesh for 3D corridor preview). This does NOT go through the IFC geometry engine.

When Rick's implementation lands in IfcOpenShell, we can optionally switch the Blender visualization to use `tool.Loader.create_generic_shape()` for consistency with how horizontal alignment segments are rendered. But we don't block on it.

**For the 2D cross-section preview specifically:** We compute the break points from widths + slopes ourselves (simple cumulative offset math), then draw them as a GPU polyline in the viewport. No IFC geometry engine needed.

## Superelevation (Future, but Design For It Now)

Superelevation rotates the cross-section around the crown or pivot point. In IFC, this is handled by:

1. **Varying slopes in `IfcOpenCrossProfileDef`** — Different slope values at different stations
2. **`IfcDerivedProfileDef`** — Apply a rotation transformation to the base profile

For Phase 1, handle superelevation by generating different `IfcOpenCrossProfileDef` instances at each station with computed slopes. This is the simplest approach and matches how Civil 3D internally resolves superelevation.

## Implementation Plan

### Phase 1: Tool Layer (`tool/alignment.py` or new `tool/cross_section.py`)

**Data structures:**

```python
@dataclass
class CrossSectionComponent:
    """Single component (lane, shoulder, curb, etc.)"""
    component_type: str          # "LANE", "SHOULDER", "CURB", etc.
    width: float                 # Width in meters
    slope: float                 # Cross-slope (e.g., -0.02 for -2%)
    tag_start: str               # Tag at start point (inherited from previous)
    tag_end: str                 # Tag at end point

@dataclass
class CrossSectionAssembly:
    """Complete cross-section (collection of components)"""
    name: str
    left_components: list[CrossSectionComponent]   # Ordered outside-in
    right_components: list[CrossSectionComponent]   # Ordered inside-out
    crown_tag: str = "CL"
```

**Profile generation methods:**

```python
@classmethod
def assembly_to_open_profile(cls, assembly, ifc_file):
    """Convert assembly to IfcOpenCrossProfileDef.
    
    Concatenates left (reversed) + right components into
    a single widths/slopes/tags list.
    Returns: IfcOpenCrossProfileDef entity
    """

@classmethod
def compute_break_points(cls, widths, slopes, horizontal_widths=True):
    """Compute 2D (x, y) coordinates of break points from widths and slopes.
    
    This is the LOCAL geometry computation used for Blender preview,
    independent of the IFC geometry engine (which doesn't support
    IfcOpenCrossProfileDef yet — see IfcOpenShell #7338).
    
    Starting from (0, 0), each segment extends by width at given slope.
    If horizontal_widths=True, width is horizontal distance.
    If False, width is along-slope distance.
    
    Returns: list of (x, y) tuples, length = len(widths) + 1
    """

@classmethod
def create_section_preview_mesh(cls, assembly):
    """Create a Blender polyline mesh for 2D cross-section preview.
    
    Uses compute_break_points() to generate coordinates, then
    creates a Blender mesh with edges (no faces — it's an open profile).
    Does NOT use tool.Loader.create_generic_shape().
    """

@classmethod
def create_sectioned_surface(cls, ifc_file, directrix, profiles, stations):
    """Create IfcSectionedSurface from profiles at stations.
    
    Args:
        directrix: IfcCurve (3D alignment curve)
        profiles: list of IfcOpenCrossProfileDef (one per station)
        stations: list of float (distance along alignment)
    Returns: IfcSectionedSurface entity
    """
```

## Relationship to Corridor (Next Spec)

This spec defines the PROFILE. The corridor spec will define the SWEEP. The boundary is:

| This Spec (Cross-Sections) | Corridor Spec (Next) |
|---------------------------|---------------------|
| `IfcOpenCrossProfileDef` creation | `IfcSectionedSurface` creation |
| Assembly/template definition | Station interval calculation |
| Component width/slope/tag editing | Profile placement along alignment |
| Standard template library | Superelevation applied to profiles |
| 2D preview | 3D corridor visualization |
| Single profile at a point | Multiple profiles varying along alignment |

The corridor spec will consume assemblies from this spec and sweep them along the alignment directrix from the vertical alignment spec.

## Key IFC References

- `IfcOpenCrossProfileDef`: Profile defined by widths and slopes — the preferred roadway approach
- `IfcSectionedSurface`: Open profile sweep (surface, not solid) — our corridor geometry target
- `IfcSectionedSolidHorizontal`: Closed profile sweep (solid) — for pavement courses later
- `IfcCompositeProfileDef`: Multiple profiles combined — for complex multi-layer sections
- `IfcDerivedProfileDef`: Transformed profile — for superelevation rotation
- `IfcAxis2PlacementLinear` + `IfcPointByDistanceExpression`: Station-based positioning
